# PON MVP仕様・受入基準（たたき台）

更新日：2026-10-14  
状態：実装前の仕様案。未実装機能を提供中と表示しない。

## 1. 目的

PONの最初の価値を、投稿者が「頭の中の発想を少し整理できた」と感じることに置く。利用者層は最初から広く保ち、初期に絞るのは機能の範囲であって、利用者やアイデアの種類ではない。

## 2. MVPで検証する仮説

1. 事業計画なし・一文から始められれば、入力への心理的抵抗が下がる。
2. AIが課題・対象者・解決案・未確定事項を整理すると、自由記述だけより他人に説明しやすくなる。
3. AIの出力を本人が編集でき、推測が明示されれば、利用者は結果を自分の考えとして確認・修正できる。
4. 公開や協業を強制せず、非公開のまま終了できれば、機密性への不安を抑えられる。
5. 利用者が次の行動を自分で選べることが、単なる文章生成との差になる。

## 3. 初期スコープ

### P0：最初に成立させるもの

- LPから「試す／意見を送る」導線を設ける（実装されるまで偽の送信成功を表示しない）。
- テキスト一文から開始できる入力画面。
- 整理結果に「課題」「想定する人」「解決案」「分かっていること」「未確認・仮定」を表示する。
- 出力を編集・再生成・破棄できる。
- 初期状態は非公開。公開は別の明示操作と確認を必要とする。
- 機能が未実装の場合、サンプル画面は「デモ／イメージ」と明記する。

### P1：P0の価値を確認した後

- 下書き保存・削除
- 画像や資料の任意添付
- テンプレート型の概念図・画面モックアップ
- 簡易コスト計算（入力値と仮定を併記）
- 匿名での反応収集、通報・削除依頼

### 初期対象外

- 決済、送金、投資・融資仲介
- 自動契約、権利の自動判定
- 実動作アプリの完全自動生成
- 利用者間の自由なDMや、本人確認前の直接連絡先交換
- AI出力を検証済み市場データ・確定見積もりとして扱うこと

## 4. 画面・フロー要件

1. **入口**：一文でもよいと伝え、日常の不便・仕事の改善・発明・新サービス等の複数例を示す。
2. **入力**：短い説明を任意入力。長いフォームや属性登録を必須にしない。
3. **整理中**：処理失敗時は再試行とテンプレートによる手動整理を案内する。無限リトライは禁止。
4. **結果**：事実と推測を分ける。AIが補った内容は仮定として示し、本人が編集できる。
5. **次の一手**：「下書きとして終了」「可視化」「需要を確かめる」などを並列の選択肢として提示する。公開・起業・協業を必須にしない。
6. **公開設定**：初期値は非公開。公開対象・公開情報・取り消し方法を確認画面で示す。

## 5. プライバシー・信頼の必須条件

- 公開前の個人名、メール、電話、SNS、住所、勤務先等を勝手に表示しない。
- マッチング時も、本人が開示項目と相手を確認して同意するまで連絡先を渡さない。
- 本人確認が必要な段階では外部サービスの利用を検討し、本人確認書類画像やマイナンバーをPONで保管しない設計を優先する。
- 「匿名だから絶対に特定されない」「アイデアを盗まれない」と保証しない。
- 公開範囲、データ保存期間、削除方法、AI処理に送る情報を利用者に説明する。
- APIキーはブラウザ側に含めず、サーバー側の環境変数で管理する。
- API利用に上限・レート制限・タイムアウト・再試行上限を設ける。支出上限に達したら有料APIを停止し、代替案を表示する。
- 添付ファイルや投稿内容に含まれる個人情報・機密情報・権利侵害に注意喚起する。
- 通報・削除依頼と、運営者が確認する手段を公開機能より先に設計する。

## 6. MVP受入テスト

| ID | テスト | 合格条件 |
|---|---|---|
| AC-01 | 一文だけ入力 | 長文や事業計画なしで次に進める |
| AC-02 | 日常の困りごとを入力 | 起業・収益化を強制しない整理結果になる |
| AC-03 | 不明点の多いアイデアを入力 | 不明点を事実のように捏造せず「未確認」と表示 |
| AC-04 | AIの解釈が間違っている | 利用者が編集・削除できる |
| AC-05 | 結果画面で終了 | 公開や登録を強制されない |
| AC-06 | 公開操作を選ばない | 下書きが公開状態にならない |
| AC-07 | 公開を選ぶ | 公開情報と公開範囲を最終確認できる |
| AC-08 | APIキーをブラウザから調査 | ソース・通信レスポンスに秘密鍵が露出しない |
| AC-09 | API障害・上限到達 | 無限再試行せず、費用を増やさずエラー案内を表示 |
| AC-10 | 削除依頼 | 利用者が手順を見つけられ、運営側で対応可能 |
| AC-11 | モバイル表示 | 横スクロール・重なり・読めない文字がない |
| AC-12 | デモ画面を見る | 実装済み機能と誤認しない表示がある |

## 7. 需要検証の最低限の進め方

- 異なる立場の候補者にLPを見せ、「何のサービスだと理解したか」を先に自由回答で聞く。
- 「自分なら何を入力するか」「何が不安か」「次に何をしたいか」を聞く。
- 日常の不便、仕事改善、発明・事業案を例にして、利用者層を絞るのではなく説明の偏りを点検する。
- 反応数を需要の証明と扱わず、具体的な入力行動、再利用意向、支払意思を区別する。
- 少数の聞き取り結果を市場全体に一般化しない。

## 8. 公開前チェックリスト

- [ ] LPをPC・スマートフォンで確認
- [ ] デモと実機能の区別を確認
- [ ] 利用規約・プライバシー説明・問い合わせ先を用意
- [ ] 投稿・削除・通報の運用責任者と手順を決定
- [ ] 秘密情報がクライアントに出ないことを確認
- [ ] API利用上限・ログの個人情報・保存期間を確認
- [ ] アクセシビリティ（キーボード操作、コントラスト、ラベル）を確認
- [ ] 未実装機能を利用可能と誤認させるCTAがないことを確認
- [ ] 実際の利用者による理解度テストを実施

## 9. 重要な判断原則

- 利用者層は広く維持し、体験と機能を段階的に作る。
- AIの結果は草案であり、本人の確認を経て採用する。
- 需要の意向と実購入、見積もりと実コスト、匿名表示と本人確認済みを混同しない。
- 安全性・費用上限・削除手順が成立する前に、公開投稿やマッチングを急がない。
