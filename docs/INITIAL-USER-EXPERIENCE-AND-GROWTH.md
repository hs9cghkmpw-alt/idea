# PON 初期利用体験・利用者獲得戦略

更新日：2026-10-14  
位置づけ：構想段階の仮説。利用者インタビュー・行動データによる検証前であり、実証済みの結論ではない。

## 1. 固定方針

**利用者層を最初から狭めない。** PONは、個人、学生、会社員、個人事業主、経営者、企業、開発者、デザイナー、地域団体などを広く受け入れる構想とする。アイデアも日常の小さな不便、仕事の改善、地域課題、発明、新サービス、事業構想などに限定しない。

初期に絞るのは「誰が使えるか」ではなく、実装する機能の順番、利用開始時の負担、検証する仮説である。LPやプロダクトで特定の属性だけを歓迎するような表現をしない。

## 2. 参加者を役割で考える（排他的なユーザー区分にしない）

1. **思いつきを持ち込む人**：一文や雑なメモから始めたい。
2. **アイデアを整理・可視化したい人**：他人に伝わる形にしたい。
3. **反応や需要を知りたい人**：必要とされるか、何が伝わらないかを知りたい。
4. **実現を手伝える人**：開発、デザイン、製造、運営、調査などで協力できる。
5. **課題・技術・市場の視点を持つ人や組織**：新しい解決策や協業候補を探したい。
6. **まず閲覧・参加したい人**：投稿や起業を決めずに、見て学び、コメントするところから参加したい。

一人が複数の役割を持てる。個人か企業か、投稿者か協力者かを固定しすぎず、行動に応じて参加方法を選べる設計にする。

## 3. 利用開始の心理的ハードルを下げる

初回の利用体験で求めることは、最小限にする。

- 長い説明や事業計画を要求しない。
- 一文でも開始できることを明確に伝える。
- すぐに起業・公開・協業するよう迫らない。
- 投稿前に「公開する情報」「まだ見せない情報」を選べる設計を目指す。
- 最初の結果は、投稿者が読んで「自分の考えが少し整理された」と感じるものにする。
- AIが補った内容は、本人が修正・削除でき、推測と確認済み情報を区別する。
- 公開や協業は後から選択できるようにする。投稿をしたことを、公開や権利放棄への同意と扱わない。

## 4. 推奨する初回フロー

1. **きっかけ**：「こんなのあったらいいのに」「この作業、もっと楽にならない？」などの例から入る。
2. **自由入力**：一文、箇条書き、困りごとの説明のどれでもよい。
3. **整理結果**：課題、誰にとっての問題か、解決案、未確定事項を短く提示する。
4. **本人による修正**：AIの解釈が違えば直せる。
5. **公開範囲を選択**：まず非公開で整理する選択肢を用意し、公開は明示的な選択にする。
6. **次の一手を選ぶ**：「ここで保存」「イメージを作る」「他人の反応を聞く」「協力者を探す」など。すべてを必須にしない。

MVPでは、実装コストと安全性を確認しながら、自由入力・基本整理・非公開下書き・テンプレート型可視化を優先候補とする。公開フィード、本人確認、メッセージ、マッチング、決済を最初から同時に実装する前提にはしない。

## 5. 初期の価値提案

PONの価値は「AIで画像を作れる」だけでは弱い。画像生成だけなら他サービスでも可能で、継続利用の理由になりにくい。

中核価値の仮説は次の組み合わせである。

- **言語化**：うまく説明できない発想を整理する。
- **可視化**：他人に説明できる形にする。
- **検証**：仮説・不明点・必要な調査を明確にする。
- **選択肢**：本人の意思に応じて、反応収集や協業の可能性へ進める。

長期的な差別化候補は、アイデアの投稿数そのものよりも「発想を他人が理解できる状態にし、次に何を試せばいいか分かる状態まで支援する」こと。これは利用者の反応で検証する。

## 6. 初期集客の考え方

### 先に試すチャネル
- **具体例を見せる短い投稿**：雑な一文が、整理されたアイデアや画面案になる前後を見せる。
- **日常課題を題材にした記事**：「こんな不便を解決するなら？」と問い、PONの考え方を伝える。
- **開発過程の公開**：設計上の判断、安全性の課題、試作の変化を記録する。
- **役割の異なる人からの意見収集**：投稿したい人だけでなく、見て意見を言う人、作る人、企業側の視点も聞く。

### 避けること
- 「誰でも必ず儲かる」「アイデアが盗まれない」などの保証。
- 実装されていないAI生成、投稿、マッチング機能を利用可能と誤認させる表現。
- 反応数や登録者数を捏造すること。
- 広告収入でAI費用を必ず賄えるという前提。
- 最初から大量の機能や登録項目を見せること。

## 7. 検証指標

訪問者数だけで需要を判断しない。実際の行動と、離脱理由を組み合わせる。

| 段階 | 指標 | 確認したいこと |
|---|---|---|
| 認知 | LP訪問、流入元 | どの説明が人を連れてくるか |
| 理解 | 主要セクション閲覧、簡易インタビュー | PONを何のサービスと理解したか |
| 関心 | 具体的な意見・協力意思 | 何に価値を感じ、何を不安に思うか |
| 初回価値 | アイデア入力完了率、整理結果の修正・保存 | 入力負担に見合う価値があるか |
| 継続 | 再訪、2件目の入力、他者への共有 | 一度きりで終わらない理由があるか |
| 協業 | 関心表明、具体的な協力提案 | マッチングが本当に必要か |

現時点で実装されていないイベント計測や登録機能は、存在するものとして扱わない。まずLP上でできるのは、誤認のない説明と、利用者候補への聞き取り・意見収集の導線を整えること。

## 8. 需要検証の進め方

1. LPを複数の立場の人に見せ、30秒で「何のサービスだと思ったか」を聞く。
2. 「自分なら何を入力するか」「何が不安か」「次に何をしたいか」を自由回答で集める。
3. 日常課題・仕事改善・発明/事業案など、異なる例を使って理解度を比較する。対象者を限定するためではなく、表現が特定の層だけに偏っていないかを見る。
4. 入力例から手作業でも整理結果を作り、利用者が本当に役立つと感じるか確認する。
5. 価値が確認できた機能から実装し、実際の利用データを取る。

## 9. 現段階の優先順位

1. LPで「誰でも・どんな段階でもよい」を明確に伝える。
2. 構想図と利用例が、実機能と誤認されないようにする。
3. 何を作るかだけでなく、何をまだ作っていないかを明記する。
4. 初回体験を自由入力→整理→本人修正→公開範囲選択→任意の次の一手に整理する。
5. 需要の兆候を得てから、投稿・保存・AI処理・公開・協業の実装順を決める。
6. セキュリティ、プライバシー、AI費用上限を、公開機能の実装前に具体化する。

## 10. 未解決のリスク

- 入口が広いことは、価値が伝わりやすいことを保証しない。
- 投稿者だけが増え、閲覧者や反応が増えない可能性がある。
- 多様なアイデアを扱うほど、整理品質・モデレーション・権利侵害への対応が複雑になる。
- AI整理が一般的な要約に留まると、他サービスとの差が弱い。
- 「匿名」「保護」を強く約束しすぎると、実装で担保できない範囲まで期待させる。

したがって、方針は「利用者を狭めない」で固定しつつ、初期検証では利用者の違いを観察し、どの体験・表現・機能が各人に有効かを学習する。観察結果は利用者の排除ではなく、体験の最適化に使う。
