# PON 初回体験・画面仕様（実装引き継ぎ用）

更新日：2026-10-14  
対象：PONの最初の利用体験  
状態：画面・挙動の仕様案。実装済みではない。

## 0. 設計の固定条件

- 利用者層は最初から広く保つ。個人・学生・会社員・事業者・企業・開発者・地域活動などを入口で排除しない。
- 入口は軽く、まず一文で始められる。
- アイデア投稿と、公開・マッチング・本人確認を別の段階にする。
- 新規アイデアは非公開を初期値とする。
- AIの整理結果は草案であり、事実と推測を区別し、本人が編集できる。
- 画面モックアップは実際に動作するアプリや市場検証の証拠と混同させない。
- 実装されていない処理を、成功したように見せない。
- API費用が発生する処理は上限・回数制限・失敗時の代替を設計する。

## 1. 最小ユーザーフロー

`LP → 一文入力 → 整理結果 → 編集／やり直し → 次の行動を選択`

この時点でユーザーは終了してよい。登録、公開、起業、マッチングは必須にしない。

### 画面A：LP／入口

**目的：** 何のサービスかを短時間で理解し、気軽に試せそうだと感じてもらう。

必須表示：
- 「一文の思いつきからでいい」
- 日常の不便、仕事・地域の改善、発明、新サービスなどの異なる例
- 利用者層は限定されていないこと
- 実際に使える機能と、構想・開発中の機能の区別
- プライバシーの要点と問い合わせ・意見送信先（実装後）

主CTA：
- 実装前：試作・構想の説明へ誘導する。実際には動かない入力フォームを置かない。
- 実装後：「アイデアを整理する」。CTAは実際の入力画面につなぐ。

副CTA：
- 「仕組み・安全性を見る」
- 「意見を送る」（フォームが実装されるまでは送信成功を装わない）

受入条件：
- 初見の利用者が自分の言葉でサービスの目的を説明できる。
- 開発中の機能を、今すぐ利用できると誤解しない。

### 画面B：一文入力

**目的：** 事業計画や専門用語なしに、考えを外へ出せるようにする。

フィールド：
- アイデアの説明（必須、短文可）
- 任意の補足（任意）
- 「何が不便？」「誰に役立つ？」「こうなったらいい」などの任意ヒント

最初の段階では要求しない情報：
- 実名、住所、電話番号、勤務先、SNS
- 事業計画、収益予測、技術仕様、専門知識
- アイデアの公開許可

安全表示：
- 「個人情報・会社の機密情報・他人の非公開情報は入力しないでください」
- 「送信する情報がAI処理に使われる場合は、その範囲と保存条件を送信前に説明する」
- 実装では、データ送信先と保存条件を説明できない限り、実際の入力送信を有効にしない。

操作：
- 「整理する」
- 「戻る」
- 入力の消去

受入条件：
- 空欄のまま送信できない。
- 一文で進められる。
- 二重送信を防ぐ。
- 通信中、失敗、上限到達を明確に表示する。
- 失敗時に勝手に何度も有料APIを呼ばない。

### 画面C：整理結果

**目的：** 自分の考えを、説明・検討しやすい構造にする。

表示ブロック：
1. アイデアの要約
2. 解決したい課題
3. 想定する人・場面
4. 提案する解決方法
5. すでに分かっていること（利用者の入力に基づく）
6. 未確認の点・AIが置いた仮定
7. 次に確認するとよい質問

重要な表示ルール：
- 入力にない市場規模、価格、法令、実現可能性を確定事実として生成しない。
- 根拠のない数値は出さず、「未確認」とする。
- AIが補った内容は「仮説／要確認」と表示する。
- すべてのブロックを利用者が編集・削除できる。
- 元の入力を上書きせず、変更前に戻せる設計を検討する。

操作：
- 「ここを編集」
- 「別の表現にする」
- 「最初からやり直す」
- 「この内容で続ける」
- 「終了する」

受入条件：
- 生成結果が間違っていても、利用者が訂正できる。
- 推測と事実の違いを利用者が説明できる。
- 「AIが言ったから正しい」と受け取らせる見せ方をしない。

### 画面D：次の行動

**目的：** 起業や公開へ誘導せず、利用者自身が次の行動を選ぶ。

選択肢：
- **ここで終了：** 保存しない場合は、そのことを明示する。
- **下書きに保存：** アカウント・保存機能が実装された後に提供する。
- **イメージ化：** まずはテンプレート型の簡易図・画面モックを作る。
- **需要を確かめる：** 公開範囲とデータの扱いを決めてから進む。
- **協力者を探す：** 将来機能。本人確認・同意・通報・権限制御が整うまでは利用可能と表示しない。

受入条件：
- どの選択肢も、公開・起業・協業を強制しない。
- まだ利用できない選択肢は「開発中」と明示する。
- 選択しなくても不利益がない。

### 画面E：公開確認（将来機能）

公開操作は整理画面と分離し、初期値は非公開にする。

公開前に確認する項目：
- 誰が閲覧できるか
- どのフィールド・添付資料が見えるか
- 氏名・連絡先・勤務先等が含まれていないか
- 公開後にコピー・保存される可能性があること
- 公開の取り消し方法と、取り消しても既に複製された情報は回収できないこと

公開実装の必須条件：
- サーバー側の認可チェック
- 非公開情報がAPIレスポンスや添付URLから取得できないこと
- 公開範囲変更の監査ログ
- 削除・通報・管理者対応の手順

## 2. エラー状態の標準

| 状態 | 表示・対応 |
|---|---|
| 入力不足 | 何が必要かを短く表示。内容を失わない |
| 通信失敗 | 再試行ボタンを出す。自動無限再試行は禁止 |
| AI利用上限 | 上限に達したことを説明し、無料の手動整理テンプレートを案内 |
| AI出力が空／壊れている | 結果を成功扱いにしない。再試行または手動編集へ |
| 保存失敗 | 保存されていないと明示し、入力を保持する |
| 認証切れ | 入力内容を失わないようにし、必要な操作だけ再認証を求める |
| 不適切・機密情報の疑い | 確定的に断罪せず、見直しを促す。機械判定だけで永久停止しない |

## 3. 無料優先の実装アーキテクチャ案

### 第1段階：静的LPとローカル試作
- HTML/CSS/JavaScriptでLPと操作可能なUIプロトタイプを作る。
- デモデータは明確にデモと表示する。
- ユーザー入力を外部に送信しないローカルデモを用意できる。
- 認証・保存・公開・AI処理がない状態では、それらが存在するように見せない。

### 第2段階：ローカルまたはサーバー側のルールベース整理
- テンプレートに沿って入力を整理し、外部APIなしでも基本の体験を検証する。
- 出力は「入力から抽出した内容」「本人が追記する欄」「未確認の問い」を分ける。
- この段階で入力完了率、理解度、編集しやすさを確認する。

### 第3段階：AI APIの限定導入
- サーバー側だけにAPIキーを置く。
- ユーザーごとの回数制限、月額支出上限、タイムアウト、再試行上限を実装する。
- 上限到達時に有料APIを止め、テンプレート方式へ切り替える。
- APIプロバイダーのデータ保持・学習利用・地域・規約を確認してから、送信する情報を決める。

### 第4段階：保存・公開
- 認証、投稿者所有権、公開範囲、削除、通報、監査ログを先に実装する。
- 公開機能をAI機能より先に急がない。
- 非公開投稿の認可テストが通るまでは、他人が閲覧できる公開投稿・マッチングを有効にしない。

## 4. 最小の計測イベント

個人情報やアイデア本文を分析イベントに送らず、次の件数・状態だけを計測する。

- `landing_view`
- `idea_input_started`
- `idea_input_submitted`
- `draft_result_shown`
- `result_edited`
- `next_step_selected`（選択肢の種類のみ）
- `flow_abandoned`（本文を含めない）
- `error_type`（エラー分類のみ）

必要以上にユーザーを追跡しない。分析のためにアイデア本文、氏名、メール、機密情報をイベントへ複製しない。

## 5. 実装着手前の決定事項

- [ ] ローカル試作は外部通信なしで成立するか
- [ ] 下書きをブラウザ内に保存するか（共有端末での漏えいに注意）
- [ ] AIプロバイダーと送信するデータ範囲
- [ ] 保存期間と削除手段
- [ ] ログに保存する項目
- [ ] 無料利用の上限と有料API停止条件
- [ ] 問い合わせ・削除依頼・権利侵害申告の窓口
- [ ] 公開・限定公開機能を有効にするための受入テスト

## 6. 最小の成功条件

最初のリリースで確認したいのは登録者数ではなく、次の事実である。

1. 多様な立場の人が、サービスの目的を正しく理解できる。
2. 一文から入力を開始し、自分の考えを整理した結果を得られる。
3. AIの仮説を修正できる。
4. 公開せずに終了できることが分かる。
5. 入力に対するプライバシー不安と、再利用したい理由を把握できる。

この条件を確認してから、保存・公開・需要検証・協業へ進む。
