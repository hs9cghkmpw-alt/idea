## 2. PONの全体像

PONは、未完成のアイデアを気軽に投稿し、整理・可視化・検証し、本人が希望する場合に協力者や企業との協業につなげることを目指すプラットフォーム。

- 対象者は初期から広く維持する。個人、学生、会社員、クリエイター、企業、地域活動などに限定しない。
- 入口を軽くし、未完成のアイデアでも扱えるようにする。
- アイデア投稿、AI等による整理・可視化、需要・コストの検証、希望に基づく協業を段階的に実現する。
- 公開範囲、サーバー側の認可、情報の最小化、同意、通報・削除、原価上限を前提に設計する。
- PONは当面、資金を預かったり送金したりしない。出資・融資等の仲介や決済機能は、法的・運営上の確認なしに追加しない。
- 仕様書やモックアップに記載された機能は、それだけでは実装済みではない。

### 添付機能の設計案（まだ未確定・未実装）

- 非公開Supabase Storageバケットを使用し、公開バケットにしない。
- メタデータ用の `public.idea_attachments` テーブル、RLS、Storageポリシーを新設する。
- アイデア所有者だけが添付をアップロード・削除できるようにする。公開済みのコミュニティアイデアを読めるユーザーには、そのアイデアに紐づく添付の閲覧を許可するか、仕様と脅威モデルを確認して明示的に定める。
- ファイルアクセスは権限確認後に短時間有効な署名付きURLを使う設計を検討する。Storageポリシー自体も認可を強制する。
- パスにユーザーID・アイデアID・添付IDを使い、他人のファイルを推測して操作できないようにする。
- 許可候補：JPEG、PNG、WebP、PDF、DOCX、XLSX、PPTX。SVG、HTML、実行ファイル、マクロ有効Office形式、旧式Office形式は除外する。
- 暫定上限案：20 MB／ファイル、5ファイル／アイデア、50 MB／アイデア。実装前にStorageの制限・検証方法・運用費用を確認する。
- 拡張子やブラウザーのMIME判定だけを信用しない。サーバー側のサイズ・形式・所有権制約を設ける。
- アップロード中に編集画面を閉じない。失敗時の再試行と部分失敗を扱う。
- PostgreSQLの外部キーによるメタデータ削除だけではStorageの実ファイルは消えない。アイデア削除時のファイルとメタデータの整合性、失敗後の再試行・孤立ファイル清掃を設計する。
- Free Studioの初期追加候補は、テキスト／Markdown等をファイルとして出力する機能。AI連携や有料APIは別途承認なしに追加しない。

## 6. 次の作業手順

別PCで作業を再開したら、次の順で進める。

1. リポジトリを開き、`git status --short --branch`、`git branch -avv`、`git log -5 --oneline --decorate` を実行する。
2. GitHub上の最新ブランチとローカルHEADを照合する。未プッシュの旧PCブランチがあると決めつけない。
3. この文書と `README.md`、`docs/PON-STRATEGY-SUMMARY.md`、`app/mvp/package.json`、既存マイグレーションを確認する。
4. 基準ブランチから添付機能用ブランチを用意する。作業前に差分を確認し、既存変更を上書きしない。
5. 添付用マイグレーションを追加する。テーブル、RLS、Storageポリシー、サイズ・形式制限、公開／非公開アクセスをレビューする。
6. UIとアップロード・ダウンロード・削除フローを実装する。失敗・再試行・孤立ファイルも扱う。
7. 権限テスト、正常系／異常系テスト、`npm.cmd test`、`npm.cmd run build` を実行し、結果を記録する。
8. コードレビューとセキュリティレビューを行い、引き継ぎ書を更新する。
9. PR作成、ホストDBへのマイグレーション適用、Renderデプロイは、それぞれ必要な確認を取ってから進める。

## 7. 安全・変更管理のルール

- Supabaseの `service_role` キーや秘密情報を、ソース、引き継ぎ書、Issue、ログ、チャットに貼らない。クライアントには公開用Publishable/anonキーだけを使う。
- 本番DBにSQLを適用する前に、差分・対象プロジェクト・バックアップ／復旧策・ロールバック方針を確認する。
- Renderへのデプロイ、課金サービス契約、請求を発生させる設定変更は、事前に明示的な承認を得る。
- ユーザーの許可なく、GitHubの既定ブランチへ直接コードを追加・変更したり、PRをマージしたりしない。文書更新の共有方法も、作業者に説明してから進める。
- テストで確認したことと、未確認のことを明確に区別する。
- セキュリティやプライバシーの問題を、見た目の動作だけで「解決済み」としない。
- ユーザーが別のPCに移るときは、引き継ぎ書とGitHub上の実際の状態を優先し、過去のローカルパス・未コミット変更・環境変数が存在すると仮定しない。
