# PON データモデル・プライバシー脅威モデル

更新日：2026-10-14  
対象：MVPの設計・実装前レビュー  
状態：**設計案。実装・セキュリティ監査済みを意味しない。**

## 1. 目的と設計原則

PONは利用者層を最初から広く保つ。入力内容や利用目的は限定しない一方、データへのアクセス権は最小化する。

1. 新規アイデアは非公開を初期値とし、公開操作を別の明示的な手順にする。
2. ログイン状態やURLを知っていることだけを認可根拠にしない。サーバー側で毎回所有権・共有権限を確認する。
3. 公開用の要約と、投稿者が入力した原文・添付資料を別のデータとして扱う。
4. AI出力は未検証の提案として扱い、投稿者が確認・編集できるようにする。
5. アイデア本文や個人情報を、アクセスログ・分析イベント・エラー追跡へ不用意に複製しない。
6. 本人確認書類画像・マイナンバーはPONで収集・保存しない。外部確認サービスの結果も必要最小限にする。
7. 機能が未実装の段階では、UI・LPで利用可能だと誤認させない。

## 2. 最小データモデル案

| エンティティ | 最小限の属性案 | 注意点 |
|---|---|---|
| Account | 内部ID、認証プロバイダー識別子、作成日時、状態 | 公開プロフィールと認証用情報を分離。不要な住所・生年月日は集めない |
| PublicProfile | 内部ID、ニックネーム、任意の紹介文、任意の組織情報 | メール・電話・本名を公開プロフィールに含めない |
| IdeaDraft | ID、所有者ID、原文、作成・更新日時、状態 | 原文は既定で非公開。IDだけで閲覧できないこと |
| IdeaAnalysis | ID、下書きID、構造化結果、モデル/テンプレート版、作成日時 | 推測・未確認事項を明示。原文とアクセス権を継承 |
| IdeaArtifact | ID、下書きID、種類、保存先キー、作成日時 | 将来の添付はMVP後。公開領域と非公開領域を分け、直接公開URLを避ける |
| VisibilityGrant | 対象ID、対象種別、許可された利用者/協議、許可範囲、有効期限 | 共有相手・共有項目・期限を限定。拒否/取消を反映 |
| PublicationConsent | 対象ID、公開対象の版/ハッシュ、公開範囲、同意文面版、同意日時、撤回日時 | 「公開」ボタンの同意記録。全アイデア一括公開を避ける |
| VerificationStatus | Account ID、外部サービス識別子、結果、方式、確認日時、必要な有効期限 | 書類画像や番号は保持しない。認証済み表示を信用保証と混同しない |
| Report | ID、通報対象、カテゴリ、状態、作成日時 | 通報内容へのアクセスを担当者に限定。報復・悪用にも配慮 |
| AuditEvent | actor ID、操作種別、対象ID、結果、時刻 | 原文・秘密情報を含めない。アクセス制御・同意・管理操作を記録 |
| UsageCounter | account/匿名セッション識別子、機能、期間、回数、推定コスト | アイデア本文をキーやメタデータにしない。匿名利用時の濫用対策とのバランスを取る |

これは概念モデルであり、特定のデータベースやORMを決定するものではない。実装時は必要性を確認してからテーブルを作り、将来機能のためだけに個人情報を先取りして集めない。

## 3. 状態遷移と公開ルール

推奨する状態：

- `local_draft`：端末内のみで扱うプロトタイプ段階。サーバー保存しない。
- `private_draft`：サーバー保存する場合の非公開下書き。所有者のみアクセス可能。
- `shared_limited`：投稿者が指定した相手・項目・目的に限定して共有。
- `published`：明示的な同意が記録された公開用データだけを公開。
- `archived`：投稿者が通常一覧から退避。アクセス権は別途定義。
- `deleted`：通常アクセスを即時停止し、削除処理へ。バックアップからの消去には別の期限・手順が必要。

必須ルール：

- 作成・AI整理・保存だけでは公開状態に遷移しない。
- 公開直前に、公開される具体的な項目・表示名・公開範囲をプレビュー表示する。
- 公開同意は対象の版にひも付ける。内容や範囲が変わった場合、必要に応じて再同意を求める。
- 協議申請の承認、協議開始、氏名・連絡先の開示は別々の同意とする。
- 共有取消・ブロック後は、新しいアクセスを拒否する。既に相手が保存・撮影した複製まで消せるとは約束しない。
- 削除はUIから開始でき、削除受付・処理状態を利用者が確認できるようにする。

## 4. 認可マトリクス

| 操作者 | 非公開の原文 | 限定共有項目 | 公開用データ | 管理・通報情報 |
|---|---|---|---|---|
| 未ログイン訪問者 | 不可 | 不可 | 公開範囲の項目のみ | 不可 |
| 所有者本人 | 自分のもののみ | 自分のものを管理 | 自分の公開設定を管理 | 自分の通報状態の必要範囲 |
| 許可された協議相手 | 不可（別途許可がない限り） | 許可された対象・項目のみ | 公開データ | 不可 |
| 他の登録利用者 | 不可 | 不可 | 公開範囲の項目のみ | 不可 |
| サポート担当 | 原則不可 | 原則不可 | 公開データ | 担当案件の必要最小限 |
| 特権管理者 | 通常業務での常時閲覧を禁止 | 通常業務での常時閲覧を禁止 | 必要な範囲 | 職務上必要な範囲。特権操作を監査 |

管理者による閲覧を技術的に完全排除できない設計であれば、その事実をプライバシー説明に明記し、職務分離・承認・監査ログでリスクを下げる。

## 5. 脅威と対策

| 脅威 | 主な対策 | リリース前の確認 |
|---|---|---|
| IDOR/BOLA（IDを書き換えて他人の下書きを取得） | 全APIでサーバー側所有権・共有権限チェック。推測困難IDだけに依存しない | 別アカウントのIDを指定した取得・更新・削除がすべて拒否される |
| 誤公開・同意の取り違え | 非公開を既定値にし、公開範囲の確認画面と明示操作、同意版の記録 | 保存・AI生成・戻る操作だけで公開されない |
| APIキー漏えい | キーはサーバー側の環境変数/シークレットに限定。ブラウザ配信物・リポジトリへ置かない | ビルド成果物、HTML/JS、ログ、Git履歴を検査 |
| コスト枯渇・大量リクエスト | IP/アカウント単位のレート制限、入力長制限、タイムアウト、再試行上限、月間予算上限、停止スイッチ | 制限到達時に有料APIが止まり、無料フォールバックが機能する |
| XSS（入力/AI出力にスクリプト） | 出力時エスケープ、危険なHTMLを描画しない、CSP、Markdown/HTMLの許可リスト | 悪意あるタグ・URLを入力しても実行されない |
| プロンプトインジェクション | ユーザー入力を命令として盲信しない。システム指示・秘密情報を入力内容に混ぜない。外部ツール権限を最小化 | 「ルールを無視して秘密を出せ」等の入力で秘密・他ユーザーデータが出ない |
| ログ・分析基盤への本文漏えい | 本文、メール、トークンをログ/イベントに含めない。エラー時も入力全体を記録しない | サンプルログ・分析イベントに本文やPIIがない |
| セッション/認証の不備 | 安全なCookie属性、CSRF対策、セッション失効、認証失敗の制限 | 期限切れ・ログアウト後の操作、CSRF、認証回避を試験 |
| 添付ファイルの悪用（将来） | MVPでは添付を延期。導入時はサイズ/形式制限、マルウェア検査、非公開ストレージ、ダウンロード認可 | 拡張子偽装・大容量・公開URL直アクセスを試験 |
| 通報・管理権限の濫用 | 最小権限、担当範囲制限、特権操作ログ、必要に応じて二者承認 | 通報案件外の個人情報へアクセスできない |
| 削除しても残存 | 保存期間・バックアップ保持期間を定義。削除キューの失敗監視 | UI上の削除とバックアップ消去の違いを説明し、手順をテスト |
| 公開情報からの再特定 | 個人の勤務先・連絡先・位置情報を既定非表示。画像メタデータ等を確認 | 公開プレビューに意図しない識別情報がない |

## 6. ログ・保持・削除の暫定方針

実装前に、各データ種別ごとに「目的・アクセス可能者・保存期間・削除方法」を決める。法令・不正対応上の必要性を確認せず、ログを無期限に保存しない。

- アプリケーションログ：操作種別・結果・内部ID・時刻を中心にし、本文や認証情報を記録しない。
- セキュリティ監査ログ：権限変更、公開同意、情報開示、管理者操作等を必要最小限で記録し、改ざん耐性と閲覧制限を設ける。
- 利用分析：入力本文・氏名・連絡先を送らず、イベント名や集計値を中心にする。
- 削除：通常システムから即時に参照できなくする処理と、バックアップ等からの消去期限を区別して説明する。
- 外部AI事業者：送信データ、学習利用、保持期間、地域、委託先条件を契約前に確認する。秘密性の高いアイデアを送信するリスクをユーザーに説明する。
- 法的保全・不正調査の例外が必要な場合は、対象・根拠・承認・記録を限定し、規約・プライバシー通知と整合させる。

具体的な保存日数は、運営体制・適用法令・インシデント対応要件を確認して決める。未決定のまま「永久保存しない」とだけ約束しない。

## 7. 実装順とゲート

### Phase 0 — 静的LP / ローカルデモ
- 実データを送信・保存しない。
- サンプル内容を明確に「デモ」と表示。
- フォームが未実装なら、送信できるように見せない。

### Phase 1 — ローカル構造化・テンプレート可視化
- 可能なら端末内でテンプレート処理し、秘密の入力を外部送信しない。
- AI APIなしでの無料体験を先に成立させる。
- 出力に「入力情報」「AI/テンプレートによる推測」「未確認」を分ける。

### Phase 2 — サーバー側AI API
- サーバー側キー管理、レート制限、入力制限、支出上限、タイムアウト、停止スイッチを先に実装。
- 外部AIへの送信範囲とデータ保持条件を確認。
- 他ユーザーのデータや秘密情報をプロンプトへ混ぜない。

### Phase 3 — 認証・保存
- 認証と認可を別々に実装・試験。
- 非公開の初期値、所有者チェック、削除処理、保持期間、監査ログを完了する。
- 別アカウントを使ったアクセス制御テストを必須化。

### Phase 4 — 限定共有・公開・マッチング
- 明示的な公開同意、対象別の共有権限、撤回・ブロック・通報を実装。
- 本人確認をマッチング/協議の必要な段階で導入し、確認結果だけを最小限保持。
- 法務・プライバシー・運営対応手順を確認するまで一般公開しない。
